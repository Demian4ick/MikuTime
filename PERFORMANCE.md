## Release: измерения на живом Hyprland (2026-11-15)

Бинарник: `src-tauri/target/release/miku-focus`, 11 722 696 байт (11,18 МиБ), stripped ELF x86_64. Arch-пакет: ~5,69 МиБ; frontend с десятью PNG ~4,6 МиБ. Runtime использует системные GTK/WebKit, не включает отдельный Chromium.

Метод: `scripts/measure-performance.py`, 60 выборок с интервалом ~1с (после циклов — 30), warmup 10с, **всё дерево** Rust-host + WebKitNetworkProcess + 2 WebKitWebProcess. CPU — проценты одного логического ядра (полное ядро = 100%). Реальные интервалы учитываются; чтение `/proc` немного увеличивает общую продолжительность. Не включены Vite/npm/Cargo — измеряется release без dev-server и без компиляции.

### Вывод по ориентиру 600 МиБ

**Суммарный RSS превышает 600 МиБ — это не скрывается.** RSS повторно считает общие resident-страницы GTK/WebKit и графических библиотек в разных процессах; PSS пропорционально делит общие страницы и лучше отражает долю физической памяти приложения. По PSS здесь ~298 МиБ, по консервативному RSS ~696 МиБ. CPU в ожидании низкий.

Причина: две живые WebView с отдельными WebKit-процессами, а не загрузка всех спрайтов/аудиофайлов или бесконечный JS-loop. Аудио создаётся по требованию и освобождается; PNG декодируются только при показе, скрытый Main не получает секундные clock-события. Hyprland IPC не порождает фоновых subprocess на каждом движении.

Следующая рекомендуемая оптимизация при жёстком **RSS ≤600 МиБ**: создавать второе окно лениво и уничтожать скрытую WebView, пересоздавая её из единого Rust-состояния при переключении. Это освобождает один WebKitWebProcess, но увеличивает задержку открытия Main и требует отдельно проверить потерю несохранённых UI-черновиков и очереди реакций. В текущей версии оба окна сохраняются для быстрого переключения; нельзя утверждать, что RSS-ориентир уже выполнен.

### Границы проверки
- После 12 циклов Main↔Companion: +12,44 МиБ RSS / +6,97 МиБ PSS к первому idle Main. За последние 30с заметного непрерывного роста нет; это совместимо с кэшированием WebKit, но **не доказывает отсутствие утечек**. Многочасовой leak/soak-тест не выполнялся.
- Импорт 20-МиБ ресурсов может кратковременно увеличить память. Использован raw binary IPC, не массив JSON-чисел; PNG/JPEG ограничены 4096×4096.
- Windows не собиралась и не измерялась в этой среде.
- Release-процесс после сценария завершился с кодом 0. В `desktop.log` нет прежних Mesa/heap errors; остаётся только warning системной libayatana-appindicator о deprecated API.

## Проверки взаимодействия Wayland
- Синтетический `hyprctl sendkeystate` не подтвердил drag (геометрия не менялась); такой тест не выдаётся за физическое взаимодействие.
- Затем использован предлагаемый самим compositor протокол `zwlr_virtual_pointer_manager_v1`: test-only клиент собран существующими C/Wayland-инструментами из официального XML swaywm/wlr-protocols (6,9 КиБ), без системной установки или изменения разрешений.
- Реальное Wayland pointer-устройство подтвердило drag: `[1590,690] → [1640,719]`, правый клик открыл меню, короткий клик открыл Main. Отчёты: `real-pointer-drag.json`, `window-interaction.json`.
- Озвучка: импорт тестового WAV через GTK file chooser подтверждён, WAV/OGG декодируются GStreamer. Pulse playback stream для полностью тихого тестового WAV не подтверждён; реальная слышимая VOCALOID-озвучка не тестировалась. Это отдельная граница проверки, а не утверждение о проверенном звуке.
